# 飞书 CLI：从安装到用户授权

核对日期：2026-10-22。本版看板为空；只做文档与云空间连接。

## 1. 先检查是否已有配置

这一步在接入开始时由 Agent 执行。检查 WorkBuddy 等宿主实际运行命令的环境，不让用户自己判断是否装过、是否接好。

先发现并执行 `lark-cli --version`；有 CLI 时读取已安装官方 `lark-shared` skill 和当前只读帮助，再检查：

```sh
lark-cli auth status --json --verify
```

检查返回身份、应用是否配置、用户登录态、验证结果及当前能核实的授权范围；缺范围信息时读对应只读配置/帮助，不因字段缺失就判为未配置。不打印 access token / refresh token / App Secret，不读私信或无关数据。

| 实际检查结果 | 下一步 |
|---|---|
| 应用已配置、用户验证通过、身份正确且所需权限就绪 | 跳过第 2—4 节，复用连接；用户指定目标后按第 5—6 节验证目标访问并写入读回 |
| 应用已配置，仅登录过期或未登录 | 跳过安装和建应用，只执行第 4 节个人授权 |
| 身份正确，仅缺本任务权限 | 保留应用，按第 5 节补必要权限；不重新建应用 |
| 账号不符 | 请用户确认本次账号，按官方切换/授权流程处理；不默认退出或覆盖原配置 |
| CLI 没安装 | 由 Agent 执行第 2 节；安装后先查现有应用配置，再决定是否进入第 3 节 |
| CLI 已装但应用未配置 | 先核实可复用应用或宿主绑定；确实没有合适应用才进入第 3 节 |
| 网络错误、命令失败或结果不明 | 按实际错误排查；不能用“重新创建应用”作为通用修复 |

**只有本次确实需要创建应用，才向用户展示创建应用的图片和说明。** 不向已连接的用户讲完整安装/建应用教程。已有宿主飞书连接不必然等于 CLI 已授权；要以本次实际采用的工具验证结果为准。本包默认使用 CLI，不能只看到 WorkBuddy 里的飞书图标就宣布 CLI 可用。

**不要执行 `lark-cli install --help` 来检查用法**：1.0.96 的 Node 启动器会把任何以 install 开头的调用交给安装向导，连 --help 也会尝试升级。读取官网安装说明即可。其它子命令先读对应 skill 或该子命令帮助。

## 2. 首次安装 CLI 和官方 skills

官方 Agent 安装指引：
[飞书 CLI 安装指南](https://open.feishu.cn/document/no_class/mcp-archive/feishu-cli-installation-guide.md)。该 URL 返回 Markdown；网页工具打不开时，可由 Agent 用普通 HTTPS 工具读取。

有 Node/npm 时由 Agent 执行：

```sh
npm install -g @larksuite/cli
npx -y skills add https://open.feishu.cn --skill -y
lark-cli --version
```

第二行取自上述官方 Agent 指引，用于安装飞书官方 skills；检查安装器实际报告的目标 Agent 和安装路径。官方 GitHub 也提供 `npx skills add larksuite/cli -y -g` 路线，按宿主工具支持选其一，不重复安装两套。不复制制作者机器的全局 skills 目录。

无 Node/npm 时，由 Agent 打开 [Node.js 官方下载](https://nodejs.org/en/download)，核对当前系统、架构与 LTS 发行包，自行下载和安装；优先复用已有宿主运行时或可写用户目录。不要默认让用户下载、找安装包、填写路径。确实遇到系统确认、组织审批或工具无法代操作的安装窗口时，才把具体一步交给用户。npm 安装无需用户额外安装 Go/Python，Go/Python 是官方指南中源码构建的要求；本包客户端本身另需 Python 3。

Windows 安装后由 Agent 新开命令会话，用 `Get-Command node,npm,npx,lark-cli -ErrorAction SilentlyContinue` 和实际 `--version` 校验。若原会话尚未更新 PATH，由 Agent 使用发现的真实可执行路径，不让用户修改环境变量。PowerShell 对 npm.ps1/npx.ps1 的执行策略报错时，优先调用同目录的 `npm.cmd`/`npx.cmd`，不默认放宽系统执行策略。解释器发现和无 Python 时的官方安装路线先按 SKILL 第 1 步完成。

所有动态二维码、Markdown 和导出结果使用 SKILL 中 workspace 返回的本次目录作为 CWD；不用 skill 包作运行目录。下方二维码路径都是相对于本次工作目录，而非解压包。

不要把 npm 的全局模块目录误当 PATH：PATH 应包含 npm 可执行文件目录。遇到 EACCES 优先采用用户可写安装前缀或已有 Node 管理器；不默认 sudo、不修改无关 shell 配置。

## 3. 配置应用：让用户打开动态链接

仅在第 1 节检查确认 CLI 尚未配置应用、没有合适的可复用应用，且不在已有 OpenClaw/Hermes 飞书插件绑定环境时，由 Agent 发起；已连接的用户跳过本节：

```sh
lark-cli config init --new --brand feishu --lang zh
```

该命令会等待用户完成应用配置。Agent 用宿主支持的后台进程/交互会话保留它，读取输出中的配置 URL；**不要同步阻塞到链接过期才告诉用户**。URL 原样展示，并生成二维码：

```sh
lark-cli auth qrcode "命令实际返回的配置URL" --output "./feishu-app-setup.png"
```

输出图片放在本次工作目录。按 [整组示例第 3 组](grouped-messages.md)一次发齐真实链接/二维码、登录与账号组织核对、填表、创建按钮、成功标准及创建示例图；不要只先发下面这句概括话术，再等用户逐个按钮确认。概括提示：

> 请用自己的飞书账号打开这次的配置链接，按页面完成应用创建。页面出现创建成功后回来回复“应用建好了”，我会继续检查。

![飞书官网：应用创建界面示例](../assets/screenshots/07-feishu-app-setup.jpg)

### 应用创建：整组交接

先展示**本次动态配置链接和二维码**，再显示下面的官方原图。用户在电脑上可直接点链接；用手机时扫描本次二维码，若提示登录，用自己要保存笔记的飞书账号登录。不能用教程截图里的链接或示例二维码。

> 页面应出现“创建飞书 CLI 应用”或当前同类标题。按当前表单填写应用名称、选择头像（若页面要求）；名称可用“我的笔记助手”，不用照抄图片。核对当前账号和组织，阅读页面提示后点底部“创建”。看到成功结果后回复“应用建好了”；如果提示组织不允许创建，把提示文字告诉我，我来查官方说明。

![官方原图：完整创建表单和底部创建按钮](../assets/official/feishu-create-app.png)

[创建界面官方出处](https://www.feishu.cn/content/article/7644418854143315157)。官方未提供本包所需每种手机登录、组织审批页面的逐屏图；这些页面由当前身份及组织决定，遇到时查当前官方说明，按实际按钮引导，不虚构固定画面。

图中名称、头像只是示例，不要求照抄。协议、组织审批和权限确认由用户本人处理；组织不允许创建应用时说明实际阻碍，不能声称已接入。

创建这一整组做完后用户回复一次；由 Agent 继续读取原进程结果，若过期重新产生链接。只有取得真实应用配置后才发起个人授权并发送下一整组；这是后端依赖，不是每个按钮一轮。应用配置完成后还要执行个人 OAuth 授权，不能把建应用成功当成用户已登录。

### 已有 OpenClaw / Hermes / Lark Channel

当前 CLI 会在检测到相关宿主环境时阻止重复 init，优先 `config bind` 复用宿主应用。先读该版本 `lark-cli config bind --help` 和宿主官方说明，向用户说明将绑定哪个应用、采用何种身份。用户确认个人文档访问需 `user-default` 后才绑定；不默认 `--force` / `--force-init`。

已有应用但用户想手动提供凭证时，查当前 `config init --help` 的 `--app-id` 和 `--app-secret-stdin`；App Secret 从标准输入传，不放命令行，不要求发含密钥的截图。不要读取或复制制作者的 App ID/Secret。

## 4. 个人授权：分两轮交接

本包目标是文档和云空间，先向用户说明授权范围，然后由 Agent 发起：

```sh
lark-cli auth login --domain docs,drive --no-wait --json
```

拿到实际 `verification_url` 和 `device_code`。CLI 输出字段可能嵌套在 data 内，以实际 JSON 为准。不要自己拼装授权地址。

```sh
lark-cli auth qrcode "实际verification_url" --output "./feishu-user-auth.png"
```

**本轮按 [整组示例第 4 组](grouped-messages.md)，把本次动态链接、二维码、打开/扫码、登录、核对账号应用和权限、确认授权、成功标准及示例图一次发齐，再交还对话。组内不逐点确认。概括提示：**

> 请用你要保存资料的飞书账号打开链接，核对应用和权限后确认。完成后回复“已授权”，我再完成登录检查。

![飞书官网：用户授权界面示例](../assets/screenshots/08-feishu-user-auth.jpg)

截图里的历史示例使用 `--recommend`。**本包不照搬这条授权命令**：本机 1.0.96 的帮助已说明 --recommend 相当于全部业务域，故用上面的 docs,drive。docs/drive 也是业务域范围，并非严格最小的单项 scope；具体 scope 之后按实际错误补，不额外申请消息、邮箱、日历或 Base。

### 个人授权：整组交接

> 请打开上面这次生成的个人授权链接（或扫码），核对登录的是你自己的账号、应用是刚才配置的应用，再查看本次文档与云空间权限。确认后按当前页面的“授权”或“开通并授权”继续；若出现分步确认，按当前页面完成。看到授权成功后回复“已授权”。如果显示过期、无权授权或权限与你预期不符，把提示文字告诉我，不用重复扫码。

**下面是官方历史授权界面原图，只用于辨认账号、权限列表和确认按钮。图里勾选了多个业务域，不要照着全选；本包实际发起 docs,drive，仍要核对本次真实页面的权限。**

![官方历史原图：账号、权限与开通并授权按钮](../assets/official/feishu-user-consent.png)

[授权界面官方出处](https://www.feishu.cn/content/article/7644418854143315157)。需要用户操作的这一步，同时显示本次真实二维码和上述界面示例，明确两者用途。App Secret 不属于普通 OAuth 扫码必填信息；未出现手动凭证分支时，不让用户去找它。

**下一轮用户回复后，由 Agent 执行：**

```sh
lark-cli auth login --device-code "上一轮实际device_code"
lark-cli auth status --json --verify
```

device_code 仅在当前授权流程内保留，不放进可分享包、普通进度文件或截图。失效时沿用所选 docs,drive 范围重新发起，不能退回全权限。

## 5. 检查身份与权限

确认用户登录有效、验证通过且账号是用户本次选择的账号。CLI 配置和授权凭证由 CLI 自己保存管理，不另建第二套 token 文件。

访问个人文档使用 `--as user`。Bot 身份列出空资源不能说明用户的云空间为空。

权限失败有两层：应用后台是否开通、用户本人是否授权。用户身份缺权限时，先解释实际所需能力，再用返回的 missing_scopes 选择本任务需要的一项补授权；应用权限问题交给用户按 console_url 完成。不要机械申请报错列出的全部替代 scope。

命令 JSON 以 `ok:true` 为成功信封，错误检查 `error`；不要用旧 OpenAPI 的顶层 `code==0` 判断 CLI 成功。不要把 stdout 为空或仅退出 0 当成已验证正文。

## 6. 测试文档（经用户同意后）

本版不指定看板。用户同意单篇测试并选择自己的位置后，按当前官方 `lark-doc` 创建参考操作：

1. 将用户选定的笔记正文和来源准备好；不改写或杜撰原文。
2. 创建前核对已安装版本的参数；默认使用用户身份。
3. 立即记录实际文档 ID/URL，之后读回。
4. 核对标题、正文头中尾和图片；只有摘要时不能宣称全文完成。图片无法导入则单独报告。
5. 创建超时先核对是否已实际生成，不直接重建。测试文档不自动删除，也不改成公开可编辑。

通过后报告“基础接入已完成，飞书看板待配置”。测试文档读回后仍需用户打开验收；验收通过后按 [定时同步设置](scheduling-setup.md)继续确认频率与保存位置，创建真实宿主定时任务并试跑。未完成后台试跑不宣称自动同步已启用。
